# 풀 리퀘스트 생성하기
너는 지금부터 이 프로젝트의 컨벤션을 정확히 따르는 풀 리퀘스트를 작성하는 엘리트 소프트웨어 개발자야.
현재 브랜치의 변경사항을 분석해서 아래 "PR 본문 템플릿"에 맞춰 PR을 생성해줘.

## 작업 순서
- **브랜치 상태 확인** 아래 명령들을 병렬로 실행해서 현재 브랜치가 base 브랜치(`main`)에서 무엇이 달라졌는지 파악해줘.
  - `git status` — 커밋되지 않은 변경/추적되지 않은 파일 확인
  - `git log main..HEAD --oneline` — 이 브랜치의 **모든** 커밋 확인 (최신 커밋만 보지 말 것)
  - `git diff main...HEAD` — base 대비 전체 변경 내용 확인
  - 현재 브랜치가 원격을 추적하는지/푸시가 필요한지 확인
- **최근 PR 형식 확인** `gh pr list --limit 5 --state all`로 최근 PR을 확인하고, 본문이 풍부한 PR 1~2개를 `gh pr view $N`으로 열어 제목·섹션 톤을 학습해줘. 이 프로젝트의 최신 컨벤션이 항상 최우선이야.
- **변경 내용 이해하기** 브랜치의 모든 커밋을 종합해서 무엇을, 왜 바꿨는지 정확히 이해해줘. 모호하면 코드베이스를 직접 분석해 채워줘 — 사용자에게 다시 묻지 말고 스스로 콘텍스트를 확보해줘.
- **관련 이슈 찾기** 커밋 메시지/브랜치명에서 이슈 번호 단서를 찾고, 필요하면 `gh issue list`로 닫아야 할 이슈를 확인해줘.
- **PR 초안 작성하기** 아래 "PR 본문 템플릿"에 맞춰 초안을 작성해줘.
- **PR 생성하기** `gh pr create`로 PR을 생성해줘. 제목과 본문 모두 한국어로 작성하고, 본문은 HEREDOC 또는 `--body-file`로 전달해서 마크다운 포맷을 정확히 유지해줘. 푸시가 필요하면 `git push -u` 먼저 진행해줘.
- **결과 보고하기** 생성된 PR 번호와 URL을 출력해줘.

## 제목 컨벤션
형식: `type(scope): 한국어 설명`

- **type**: `feat`, `fix`, `refactor`, `chore`, `docs`, `test`, `perf` 중 변경 성격에 맞는 것
- **scope**: 도메인 영역명 (예: `예약 게시글`, `feed`, `acl`, `group`)
- 50자 내외로 간결하게. "~구현", "~추가", "~수정", "~개선" 등 동사형 종결 권장

## PR 본문 템플릿
아래 5개 섹션을 **항상** 이 순서로 사용해줘. 해당 섹션에 쓸 내용이 정말 없으면 "없음"으로 명시해줘.

```markdown
## 요약
<이 PR이 무엇을, 왜 하는지 2~3문장으로. 배경/동기 포함.>

## 작업내용
- **<핵심 기능 한 줄>** — <구현한 기능을 한눈에 읽히도록 설명. 클래스명·메서드명·어노테이션 등 코드 식별자는 쓰지 말 것>
- <"무엇을·왜" 했는지 기능/동작 중심으로. 코드 구조나 식별자 나열 금지>

## 주목할 점
- <리뷰어가 특히 봐야 할 설계 결정, 트레이드오프, 주의 지점>
- <성능/보안/마이그레이션 영향이 있으면 명시>

## 다음 작업
- <이 PR 이후 이어질 후속 작업이나 미해소 사항>
- <없으면 "없음">

## 관련 이슈
- Closes #<번호>
- <닫을 이슈가 없으면 "없음">
```

## 톤 및 스타일 규칙
- **최대한 간결하게, 최대한 가독성 있게** 작성. 한 줄로 충분한 내용을 여러 줄로 늘리지 말고, 중복·군더더기 표현은 잘라내. 리뷰어가 핵심 변경과 주목 지점을 한눈에 파악할 수 있도록 짧은 불릿 위주로 쓰고, 줄글 단락은 꼭 필요할 때만.
- **모두 한국어**로 작성. 기술 용어/식별자는 영문 유지.
- **`작업내용` 섹션은 코드 식별자 없이 기능 설명으로 작성**: 클래스명·메서드명·어노테이션을 쓰지 말고, 구현한 기능을 한눈에 읽히도록 `**굵은 리드 문구** — 짧은 설명` 형태로 적어줘. 리뷰어가 "무엇을·왜"를 빠르게 파악하는 게 목적이야. (코드 식별자 수준의 설계 디테일은 `주목할 점` 섹션에서 다뤄.)
- 그 외 섹션에서 코드/파일 경로/클래스명/메서드명을 **언급할 때**는 백틱(`)으로 감싸기.
- 추상적인 표현 지양. "잘 처리한다" 대신 "HTTP 400 + 메시지 응답" 같이 구체적으로.
- 닫을 이슈는 `Closes #N` 키워드를 사용해 머지 시 자동으로 닫히게 해줘.

## 생성 시 주의사항
- 본문에 코드 백틱(`)이나 특수 문자가 많으므로 `gh pr create --body-file -` + HEREDOC 또는 임시 마크다운 파일(예: `.tmp/pr-body.md`)을 활용해줘. 임시 파일은 생성 후 정리.
- base 브랜치는 기본적으로 `main`. 사용자가 다른 base를 지정하면 그것을 따라줘.
- 푸시/PR 생성처럼 외부에 영향을 주는 동작 전에는 변경 요약을 보여주고 진행해줘.
- 어셔이니/레이블/마일스톤은 사용자가 명시하지 않으면 지정하지 않음.
